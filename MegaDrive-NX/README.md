# Umbrella Mega Drive NX V3.3
Experimental Nintendo Switch homebrew port of Nuked-MD. No FPGA board required. It is a software simulation of the reconstructed chip logic rather than physical FPGA execution. Full speed is not established; upstream explicitly notes its simulation is very slow. Includes an original CC0 diagnostic ROM. Without a user ROM, it boots the diagnostic automatically. The screen backdrop should change with controller directions/B/C. This is a diagnostic, not a full game.

## Build
Use devkitPro with switch-dev, switch-sdl2, Git, Bash and Python 3.
    bash build.sh prepare
    bash build.sh
The first command generates patched source; the second additionally attempts cross-compilation and NRO packaging. Expected output: dist/Umbrella-MegaDrive-NX.nro. No compiled binary is present yet.

## Install after a successful build
Copy the NRO to /switch/Umbrella-MegaDrive-NX/Umbrella-MegaDrive-NX.nro on the SD card of an already homebrew-enabled Nintendo Switch. Place raw legally obtained ROMs (.bin, .md, .gen) in /switch/Umbrella-MegaDrive-NX/roms/. Launch via Homebrew Menu in application mode. A legitimately obtained optional tmss.bin can be placed next to the NRO; upstream supports a dummy TMSS fallback. Initial version supports one three-button controller, raw ROMs only, NTSC default.

## Controls
Directional pad/left stick: movement. Y/B/A: Mega Drive A/B/C. Plus: Start. Minus: exit. The ROM list uses A to select and B to exit.

## Validation
Pending: actual compilation/link, launch, frame timing, audio, PAL, mapper, controller and hardware tests. Audio bridge uses SDL resampling; does not guarantee uninterrupted sound. The upstream software simulation is computationally expensive and may be far slower than original hardware. This port is not a playable release.

## V1.5: filesystem IPC crash fix candidate
An Atmosphere v1.7 report for the **exact V1.4 NRO** (rebuild SHA256 matched release) identified Data Abort NULL access near `_fsFsOpenCommon` in libnx, associated with filesystem open/session handling, rather than an instruction in the 68000/Z80 simulation. V1.4 `nx_worker_stage()` opened `/switch/Umbrella-MegaDrive-NX/worker-stage.txt` from the chip worker on every 32768-clock progress event. V1.5 removes **all fopen/fclose/formatting** from chip worker stage functions; they publish an atomic in-memory snapshot. `nx_flush_worker_stage()` on the main SDL thread alone persists this to SD, no more often than every 1.2 seconds, and only when the content changes; W00 is written on launch. That should eliminate the observed high-frequency worker-thread FS IPC path. This is a hypothesis supported by symbolication, pending real console confirmation. A normal launch is A; Y remains raster bypass; host audio and sample mixing still disabled for isolation. Stage persistence is intentionally asynchronous: last stage may lag up to ~1.2s. Performance and full gameplay not validated.

## V1.8 VDP pipeline diagnostic display

## V2.1: fixed false-zero VDP/DIRECT counters
The V2.0 Switch photo displayed `ADDR 6291459` (= `0x600003`), `CPU 3707972`, `VDP 0`, `DIRECT 0`, `FRAMES 1`, and `PIXELS 0`. Crucially the Nuked-MD 68000 exposes A1..A23 as a **23-bit word address**, so the CPU's 0x600003 corresponds to physical byte addresses in the 0xC00006 / 0xC00007 area (VDP control port region). Thus the original C conditions checking `(address & 0xe00000) == 0xc00000` could never be true. This version fixes both the motherboard `VDP` and CPU-side `DIRECT` masks to `(address & 0x700000) == 0x600000`. Their counts are active low bus write **half-cycles**, not unique writes, and may still differ based on signal timing. `ADDR` continues displaying **the raw 23-bit word address in decimal**. No changes were made to the simulated chip logic or ROM. The video remains experimental and may stay black; if `DIRECT>0` and `VDP>0` it shows the CPU has reached the video port, and if pixels remain zero the next investigation concerns TMSS unlock, VDP registers, CRAM and video DAC. No runtime SD writes are reintroduced.

## V2.3: isolate the 68000's second word of a 32-bit VDP control write
The V2.2 real Switch screen (built-in X diagnostic) showed `ADDR 6291459` (raw 23-bit word address `0x600003`, physical byte `0xC00006`), `ACK 1050`, `MOVES 173`, `VDP 5466395`, `DIRECT 5466396`, `PIXELS 0` over more than 4.1 million simulated clocks. The 68000 changes addresses only 173 times before a persistent write signal is observed at the VDP register/command area, apparently awaiting DTACK. The upstream control port is accessed by a long write in our **diagnostic ROM** (`MOVE.L #$C0000000,$C00004`), whose second word is addressed as `$C00006`. V2.3 changes the embedded **diagnostic ROM only** to issue two independent 16-bit control-port commands, `MOVE.W #$C000,$C00004` and `MOVE.W #$0000,$C00004`, thereby avoiding the `$C00006` bus cycle for that command. Both occurrences (initial CRAM write and repeated colour loop) are changed. No external Super Hang-On cartridge bytes, chip algorithms, DTACK wiring, or filesystem behavior are altered. Launch **X diag 16bit** to test whether `MOVES` and `ADDR` advance beyond their previous plateau; the on-screen `PIXELS` may remain zero for other independent reasons. Launch **A normal** to verify the cartridge behavior remains as before. This experimental workaround **only isolates** the address-of-second-word handshake and is not a full hardware-level fix. Audio remains temporarily muted.

## V2.6: VDP command decode stages, not synthetic DTACK
V2.5 on Switch with the embedded diagnostic ROM showed master clocks 2,654,208; CLK transitions 176,946; MODE M5=1; DATA word 0 (last sample only); SEL 2,516,939, STB 2,516,211, RDY 1,100, ACK 1,050, MOVES 176, 1 frame, 0 pixels. The clock continues, but the CPU remains near the VDP command port. V2.6 measures the three sequential original decode predicates from Nuked-MD `VDP_ClockAsync` as cumulative half-cycle samples while an active CPU VDP write is requested: `DEC` = `i_sel0 && ((io_address & 0x738070)==0x600000)` (the internal VDP address match); `PASS` = `DEC && !i_as && (t13 || l23)` (VDP's access window); `CTRL` = `PASS && !i_rw && ((io_address & 0x0c)==0x04)` (control port write select). These don't imply completed writes, just combinational gates sampled after each FC1004_Clock. Together with `RDY` they will reveal whether a missing access window or downstream VDP write-acknowledge logic causes the stall. The chip logic, timing, controller input, external Super Hang-On ROM, and DTACK pin are not changed. No SD writes during the worker and sound output stays muted. In X diagnostic mode photograph DEC/PASS/CTRL alongside RDY and MOVES. Stable gameplay/performance not yet confirmed.


## V2.7: correct the misleading CTRL zero, verify CPU data drive
V2.6 on the physical Switch with X diagnostic displayed `DEC=11,036,619`, `PASS=11,036,619`, `CTRL=0`, `RDY=1,100`, `ACK=1,050`, `MOVES=176`, `DATA=0`, `MODE=1`, `PIXELS=0`, and `ADDR=6,291,458` (`0x600002` raw 23-bit word address, physical `0xC00004`). Inspection of the pinned Nuked-MD VDP confirms the previous `CTRL` probe was **incorrect**: the Mega Drive control port is `(io_address & 0x0c)==0` with the additional `(io_address & 2)!=0` word-address bit distinguishing it from the data port. In the real VDP decoder this is the `w131` write path and the `w130` port-selection latch. The old `(io_address & 0x0c)==0x04` check was a **false zero**, not evidence of a broken command decoder. V2.7 corrects that read-only counter, and substitutes the already-proven DEC/PASS display with `DRIVE` (number of half-cycle samples in which the 68000 data output is enabled while writing VDP space) and `WORD` (last low 16 bits of the CPU's driven data word, decimal). Existing `DATA` is the last raw VDP input data, which was previously 0. If DRIVE is zero while CPU/VDP bus writes grow, the CPU never drives the data output; if DRIVE rises and WORD is nonzero while DATA stays zero, inspect CPU-to-VDP data line routing; if both have valid words, focus on DTACK and the VDP's internal port sequencing. No chip-model algorithm, artificial DTACK signal, original Super Hang-On ROM, filesystem behavior, or sound-output status is changed. This remains an experimental diagnostic, not a playable full-speed release.


## V2.8: native console region selector (hardware jumper configuration)
The built-in diagnostic ROM remains black (VDP DTACK bus-stall investigation) regardless of cartridge region, so region mismatch alone does **not** explain the observed VDP stall. V2.8 makes the original Nuked-MD chip motherboard **region jumper inputs** selectable at boot: `Japan (NTSC 60Hz)` is the startup default, `USA (NTSC 60Hz)`, and `Europe (PAL 50Hz)`. In the ROM picker use **L/R** (or Left/Right) to cycle the region before pressing A (normal), Y (raster bypass), or X (built-in diagnostic). The selected values are inserted into the upstream `pal` and `_jap` locals before chip setup: `pal = (region==2)`, `_jap = (region==0)`; then upstream computes `md.ntsc = !pal;` and `md.jap = !_jap;` and passes `ym.i_ntsc` and `ym.i_jap` to the original motherboard chips. Importantly, `i_jap` is **active low**; the user-visible Japanese selection therefore produces `md.jap=0`. This modifies no ROM bytes, region header, VDP RTL, chip timings, or output scaling. The VDP progress-bar approximation accounts for a PAL frame's extra scanlines but the actual measurement remains the independent `FRAMES` hardware counter. No filesystem writes during simulation; sound stays muted. Both the original Super Hang-On game and the internal diagnostic remain experimental until proven on the physical Switch. Compare `X` in Japan and USA to isolate region effects from the internal VDP fault. Note Japanese NTSC and US NTSC share the nominal 60Hz but differ in the original region identification pin.


## V2.9: inside the VDP's original DTACK equation
On the physical Switch, the V2.8 Japan NTSC region trial still shows 5,898,240 master clocks, 3 completed VDP frames, 0 non-black pixel samples, MOVES=176, ACK=1050, RDY=1100, CLK=393215, CPU=9,016,268, CTRL=9,004,275, DRIVE=9,004,588, WORD=0 and DATA=0. The 68000 is held at word address 0x600002 (physical byte address 0xC00004). Neither the region jumper nor the preceding diagnostic ROM 16-bit write split solved the port handshake. The final WORD=0 is not conclusive of lost data, as it is a legitimate command word in the test sequence. V2.9 exposes *three original local combinational signals* from Nuked-MD's VDP_ClockAsync, sampled after FC1004_Clock while the CPU is requesting a VDP write: `CMD` counts w139 asserted, `PIPE` counts w146 asserted and `ASK` counts w125 asserted. In the unmodified source, w125 = cpu_sel && w146 and w117 = !(w24 || w125 || w128 || w129 || w133), where w117 is the VDP's active-low acknowledgement driver. `ASK` is **not** the same as an ACK delivered to the CPU: compare it with existing ACK and RDY. These are cumulative *signal-high half-cycle samples*, not distinct instructions or completed writes. The new fields `nx_probe_w139/w146/w125` merely copy existing gate values; the DTACK equation and all chip timing remain untouched. The earlier DRIVE and WORD readings are preserved internally, but the on-screen row is temporarily occupied by CMD/PIPE/ASK so the user need only share one photo. No ROM bytes, TMSS, SD runtime I/O, or chip equations are changed. Switch test remains required; this is not a completed playable game.


## V3.0 optional ZR SKIP / DTACK test (manual, not hardware accurate)
The last V2.9 Switch screenshot shows CMD ~3.5M samples, PIPE=1100, ASK=1100, RDY=1100, ACK=1050, MOVES=176, PIXELS=0 and the original 68000 bus held at word address 0x600002 (physical C00004). The original VDP acknowledgement equations remain the active default. To test whether the 68000 can move past a trapped VDP write, **press ZR once** after seeing the bus remain stuck. On the main-thread input scan this queues one atomic request. The chip worker checks the CPU currently has an active-low address-strobe and an active write in the 0x600000-word address region, with real DTACK not yet asserted, before arming the override. It then drives **only the 68000 i_dtack input** active-low for at most **1024 master clocks**, automatically releasing when AS rises, address changes, a read begins, or true DTACK is received. There is no automatic loop and each ZR press can request only one operation. The overlay shows `SKIP` = accepted requests and a small lamp: yellow while pulsing, green after the target transaction terminates, red for timeout/ineligible. Compare `MOVES` before and after pressing ZR: an increase indicates an instruction/bus transfer progressed, not necessarily correct VDP initialization. If the screen remains black, the VDP's write may still have failed and subsequent instructions may be invalid. **This manual override is intentionally not cycle-accurate and cannot be used as evidence that the original chip reconstruction is fixed.** It does not patch Super Hang-On or the built-in ROM, does not touch controller mapping other than assigning ZR to the debug request, and introduces no SD writes during simulation. To run the original unmodified pin behavior, simply never press ZR. Use Minus to exit. Chip-level full-speed playable graphics and sound are still unresolved.

This is **not yet evidence of a playable game**, but suggests at least some non-black native VDP pixel samples now exist. The screen disappearance is due to an existing `nx_video_show_boot` condition that returned immediately when any nonblack VDP pixels appeared. In V3.1, the original frame is drawn unmodified using the existing SDL texture, and `Video_Blit` overlays a translucent black **MOVES/ADDR/FRAMES/PIXELS/SKIP/ACK** diagnostics strip only when colour has appeared. `PIXELS` is the count of nonblack samples every seventh 32-bit framebuffer element, not full-screen pixel count. **Press L** during the simulation to toggle HUD on/off to inspect the game picture; **press ZR** to request a guarded one-off DTACK test pulse as in V3.0. No automatic skips, no change to original 68000/VDP logic or game ROM, and no runtime SD writes. Progress to 217 confirms address transitions following an injected ACK but not valid execution of Super Hang-On; for that use A normal ROM loading, not X builtin diagnostic. A coloured rectangle without a game title can be an intermediate or erroneous VDP output. If MOVES stops at 217 and no further content appears, determine the new ADDR value before deciding whether another one-shot test is warranted.


## V3.2: video pacing, single-pass UI and measured chip throughput
The user confirmed the Super Hang-On ROM runs correctly in RetroArch, which supports ROM viability but does not prove the current Nuked-MD simulation's CPU/VDP behaviour is correct. The Switch V3.1 recording previously showed a progressing 68000 bus address trace but only about two frames over more than two minutes and no game graphics. V3.2 targets a **real and measurable host-side inefficiency**: while the chip engine may take many seconds per frame, the native app was calling `Video_Blit` about 60 times per second and then separately presenting the boot panel (two SDL presentations on blank frames). This build preserves 16 ms controller polling but paces actual display updates to at most one every 120 ms. It presents either `Video_Blit` when the last completed chip-produced frame has non-black samples, or the detailed boot panel when there is no image, **never both** in the same tick. It scans non-black pixels once when a full VDP frame is published, caches the count atomically and skips redundant SDL texture uploads when `vid_counter` has not changed. The graphics HUD redraws with fresh MOVES/ADDR/SKIP/ACK telemetry even without a new completed frame. `RATE` (on both boot and image HUD) displays measured **master-clock simulation cycles per wall-clock second**, averaged over roughly 2.5 seconds; it is not game FPS and is quantized by the existing worker milestone snapshots. The original 68000, VDP, sound-chip simulation clocks and DTACK equations are untouched. Region menu and manually guarded ZR SKIP remain; never pressing ZR preserves the original chip path. No runtime SD writes, audio output still muted, and gameplay performance on real Switch is **not yet verified**. To test, select the same user ROM with A rather than X diagnostic; compare RATE and FRAMES values to V3.1, and observe if image progresses.


## V3.3: isolate optional diagnostic probe overhead with ZL
While the Super Hang-On ROM runs in RetroArch, the chip-level Nuked-MD Switch port remains much too slow and has not shown the expected game graphics. V3.3 introduces an A/B performance measurement without changing simulated hardware: **ZL toggles optional VDP high-frequency diagnostic sampling**. Compare the RATE (simulated master clocks per actual second) on the same ROM, region and frame before and after ZL, waiting at least 3 seconds for each measurement. The original FC1004_Clock, M68K_Clock, Z80_Clock, Video_PlotVDP, VRAM updates, TMSS, bus arbitration and cartridge accesses remain active on every cycle. Only auxiliary pin probes CMD/PIPE/ASK/SEL/STB/RDY/CLK and related counters stop updating in lightweight mode. Existing published values may freeze. This diagnostic can quantify how much overhead was introduced by our instrumentation; it cannot itself correct a chip handshake fault or make a chip-accurate implementation run at native speed. Use L to toggle the video HUD and ZR for a manual one-shot DTACK test. No automatic SKIP or ROM modifications. Do not mistake RATE for FPS. The physical Switch outcome is still unverified.
